### 2. 직접 요청의 HTTP 200을 실제 식단 응답으로 오인한다

main 루트 크롤러는 SCRAPER_API_KEY가 있으면 처음부터 프록시를 사용한다. test_2는 직접 요청을 우선하며 HTTP 200 및 본문 길이 > 500 조건만으로 반환한다. 식단 테이블이나 식당 링크를 확인하지 않는다. HTTP 200으로 반환된 안내·차단 페이지나 식단 없는 페이지는 프록시 전환 없이 파싱 단계로 넘어간다.

실행 로그에는 기본 식당 목록 대체와 수집 0곳이 나타나며 직접 차단 감지 또는 프록시 오류 로그가 없다. **직접 응답을 잘못 받아들이는 경로가 가장 유력하다.** 당시 응답 본문·상태·URL이 로그에 없으므로 차단 페이지의 구체적 종류는 확정할 수 없다.

로컬 mock 재현: HTTP 200, 500자 초과의 Access denied HTML을 정상 반환했고 프록시 호출은 0회였다. 실제 로컬 직접 요청은 HTTP 200, 13,779자, 식당 링크 15개, 요일 헤더가 있는 표 1개였지만 메뉴 본문은 없었다. 이는 상태·길이만으로 실제 메뉴를 검증할 수 없음을 보여준다. 로컬 응답과 GitHub 해외 runner 응답이 동일하다는 의미는 아니다.

요일 수 조건은 이미 원격 test_2에서 1일 이상으로 완화되어 있다. 따라서 운영일이 5일 미만이라는 가설만으로 현재 장애를 설명할 수 없다. JSON 저장 경로도 스크립트 기준으로 보정되어 있다.

### 3. 두 크롤러의 동시 푸시가 main 갱신도 방해한다

두 워크플로 모두 같은 cron으로 main을 체크아웃해 서로 다른 JSON을 갱신하고 pull/rebase 없이 push한다. 10월 5일 test_2가 09:00:18에 점검 시간 변경을 커밋했고, 기본 크롤러는 6개 식당을 수집했지만 후속 push가 fetch first로 거절되었다. main의 실패 표시는 이 실행에서는 크롤링 오류가 아닌 저장 충돌이다.

## 권장 해결 순서

1. 기본 크롤러와 개선 UI가 하나의 식단 JSON을 쓰도록 수집을 통합한다. 중복 수집과 푸시 충돌을 함께 줄일 수 있다.
2. 별도 크롤러 유지 시 HTTP 상태뿐 아니라 식당 링크·요일 헤더·유효 메뉴 항목을 검증하고, 무효 직접 응답은 프록시로 재시도한다. 로그에는 비밀키 없이 상태·본문 길이·검증 결과를 남긴다.
3. 수집 실패는 기존 메뉴를 보존하면서 crawl_status/error를 기록하고, Actions에서 실패로 드러나도록 한다. 점검 시간과 식단 갱신 시간을 화면에서 각각 표시한다.
4. 두 워크플로를 유지하면 동일한 concurrency 그룹으로 직렬화하고 커밋 직전 fetch/rebase 및 제한된 push 재시도를 추가한다. 스케줄 시각만 다르게 하는 것은 완전한 해결이 아니다.
5. 성공 판정에 실제 메뉴 수를 포함한다. 현재는 요일 표만 파싱해도 식당 성공 수를 증가시킬 수 있다.
